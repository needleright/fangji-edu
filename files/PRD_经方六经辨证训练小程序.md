# 经方六经辨证训练小程序 — 产品需求文档（PRD）

版本：V0.1（草稿）
日期：2026-07-28
状态：待评审

---

## 一、产品背景

参考案例：将 100 首常用经方整理为"看症状→判六经→猜方剂→翻面对答案"的闪卡式训练工具，核心训练的是临床上真实发生的思维路径——**患者主诉症状 → 六经辨证归类 → 联想候选方剂 → 鉴别 → 确定方证 → 回忆药物组成**，而不是单纯背诵条文。

原案例的关键设计亮点，也是本 PRD 要保留和强化的部分：

1. 正反面卡片结构：正面症状、背面答案（方名+组成+参考克数+六经归类）
2. 学习模式 / 测试模式 / 随机抽题 / 错题复习，覆盖"输入-输出-巩固"完整学习闭环
3. **同一方剂多种症状表达**：避免使用者只认得教材腔调的固定句式，脱离书本描述后就认不出真实患者的主诉

## 二、目标与非目标

### 目标
- 帮助中医学习者/临床医师把"100 首常用经方"训练到**看到症状能条件反射判断六经、联想鉴别方**的程度
- 提供可持续扩充内容的题库体系（新增方剂、新增症状变式不依赖推翻重做）
- 通过 AI 生成 + 人工审核的方式，低成本、批量产出高质量的症状变式题目

### 非目标（本期不做）
- 不做真实患者的在线问诊/开方功能（避免涉及医疗诊断合规风险）
- 不做医患社交、转发裂变等增长机制（可作为二期选做项，见「九、开放问题」）
- 不做多语言版本

## 三、目标用户与使用场景

| 用户角色 | 说明 | 核心诉求 |
|---|---|---|
| 中医院校学生 | 备考、跟诊前的方剂强化 | 高频刷题、记忆巩固 |
| 规培/新入职中医师 | 临床问诊时反应速度不够 | 建立"症状→方"的快速联想 |
| 有一定基础的执业医师 | 复习巩固、查漏补缺 | 错题针对性复习、鉴别方剂对比 |
| 内容管理员（你自己/团队） | 负责录入方剂、审核 AI 生成的症状变式 | 高效录入、批量审核 |

## 四、核心概念与数据结构

### 4.1 方剂（Formula）

| 字段 | 类型 | 说明 |
|---|---|---|
| formula_id | string | 唯一标识 |
| name | string | 方剂名称（如"桂枝汤"） |
| alias | string[] | 别名 |
| source | string | 出处（伤寒论/金匮要略/条文编号） |
| six_meridian | enum[] | 六经归类：太阳/阳明/少阳/太阴/少阴/厥阴（支持多选，兼证/合病情况） |
| sub_pattern | string | 细分证型（如"太阳中风证""阳明腑实证"） |
| composition | Ingredient[] | 药物组成，见下 |
| decoction_method | string | 煎服法说明 |
| pathogenesis | string | 病机简述（供答案页展示，帮助理解而非死记） |
| standard_symptom_text | string | 人工编写的"标准症状描述"（教材式，作为基准版本） |
| differential_formulas | formula_id[] | 需要鉴别的相似方剂 |
| difficulty | enum | 入门/进阶/难点 |
| tags | string[] | 症状关键词标签，用于筛选和检索 |

**Ingredient（药物组成子结构）**

| 字段 | 类型 | 说明 |
|---|---|---|
| herb_name | string | 药名 |
| dosage_gram | number | 参考剂量（克） |
| processing | string | 炮制方法（如"炙""生用"） |

### 4.2 症状变式（SymptomVariant）

```
variant_id
formula_id        // 关联方剂
text              // 变式症状描述正文
source            // "manual" 人工编写 / "ai_generated" AI生成
status            // draft待审核 / approved已通过 / rejected已驳回
generated_at
reviewed_by
reviewed_at
review_note       // 审核意见/修改记录
```

**审核状态流转（关键机制）**：

```
AI生成 → draft（待审核）
draft → approved（人工审核通过，进入正式题库）
draft → rejected（驳回，不进入题库，保留记录避免重复生成同类问题）
approved → draft（如需要下线修正，退回重审）
```

> 只有 `approved` 状态的变式才会出现在学习模式/测试模式的抽题池中，从机制上保证内容不会因 AI 幻觉而出现错误的中医症状表述。

### 4.3 用户学习记录（UserProgress）

| 字段 | 说明 |
|---|---|
| user_id | 微信 openid |
| formula_id | 对应方剂 |
| mastery_status | 未学习 / 学习中 / 已掌握 / 需加强 |
| last_practiced_at | 最近练习时间 |
| test_history | 测试模式历史作答记录（对/错、用时） |
| wrong_count | 累计答错次数（用于错题本排序权重） |

## 五、核心功能模块

### 5.1 学习模式（Learn Mode）

- 卡片正面：随机展示一条**已审核通过**的症状描述（标准版或 AI 变式，按权重随机）
- 用户心中默想六经归属 + 候选方剂，点击"翻面"查看答案
- 答案页展示：方剂名称、六经归类、药物组成+剂量、病机简述、**鉴别方剂列表**（点击可跳转对比）
- 用户主观标记本卡"已掌握 / 模糊 / 不会"，写入 UserProgress
- 支持按六经、出处、难度筛选学习范围

### 5.2 测试模式（Test Mode）

- 出题：展示症状，要求用户先选择"六经"，再选择/搜索"方剂名称"（双重判断，贴近真实辨证过程）
- 提交后立即判分并展示正确答案与解析
- 一组测试结束后展示本轮正确率、薄弱六经分布
- 错误题目自动写入错题本

### 5.3 随机抽题

- 支持"全部题库 / 未掌握 / 收藏 / 按六经筛选 / 按方剂出处筛选"的组合抽题
- 支持连续刷题（左滑/点击下一题）与计次统计

### 5.4 错题复习（错题本）

- 来源：测试模式答错 + 学习模式主观标记"不会/模糊"
- 排序：按错误次数/最近错误时间加权排序，优先复习高频错题
- 用户重新掌握后可手动/自动移出错题本（连续 N 次答对后自动移出，N 可配置）

### 5.5 内容管理后台（新增模块，原案例未提及但为必需支撑）

由于 100 首经方数据**需要从零录入**，且症状变式采用"AI 生成 + 人工审核"，因此本产品需要一个内容管理后台（不面向普通学习者，仅面向你/管理员）：

- **方剂录入**：表单化录入方剂名称、组成、剂量、六经归类、标准症状描述等（对照第四节数据结构）
- **AI 变式生成**：针对某一方剂，一键调用大模型生成 N 条症状变式草稿
- **审核队列**：列表展示所有 `draft` 状态变式，管理员可编辑文字、通过、驳回，支持批量操作
- **数据导入**：支持从 Excel/表格批量导入已整理好的方剂基础数据（减少重复手工录入）

> 建议：管理后台优先做成**网页端（PC 浏览器访问的简单后台）**，而不是塞进微信小程序里，因为录入/审核是低频、需要大量打字的管理操作，PC 网页体验远好于小程序表单；小程序只承载"学习者使用"的部分。

## 六、信息架构（小程序端，面向学习者）

```
首页
 ├─ 学习模式
 │   ├─ 选择范围（全部/按六经/按出处/按难度）
 │   └─ 卡片翻转交互
 ├─ 测试模式
 │   ├─ 选择测试范围与题量
 │   ├─ 答题（选六经 → 选方剂）
 │   └─ 结果报告（正确率、薄弱六经分析）
 ├─ 随机抽题
 ├─ 错题本
 └─ 我的
     ├─ 学习进度总览（六经掌握度雷达图）
     ├─ 收藏方剂
     └─ 设置
```

## 七、AI 生成症状变式 — 技术方案要点

1. **输入**：方剂的 `pathogenesis`（病机）+ `standard_symptom_text`（标准症状）+ `tags`（症状关键词）
2. **Prompt 设计原则**：
   - 要求大模型基于该方证的病机核心，生成"患者口语化主诉"，避免直接照抄教材条文用词
   - 明确要求**不改变证候本质**（不能生成偏离该方证病机的症状，否则会误导学习者）
   - 每次生成 3～5 条，覆盖不同的语言风格（口语化程度、症状侧重点不同）
3. **人工审核是硬性门禁**：AI 生成内容一律进入 `draft`，管理员逐条确认专业准确性后才能进入正式题库，避免出现中医术语误用或证候矛盾的问题
4. 审核通过的变式建议保留"版本追溯"，便于后续如发现问题可以整条下线（状态改回 `rejected`）而不影响其他内容

## 八、非功能性需求

| 类别 | 要求 |
|---|---|
| 平台 | 微信小程序（原生小程序 或 uni-app 跨端方案，视团队人力而定） |
| 账号体系 | 微信一键登录（openid），无需额外注册 |
| 后端建议 | 数据量小（100方剂+若干变式），可用微信云开发/云托管，或自建轻量后端（如 FastAPI + PostgreSQL），两种方案均可，取决于是否需要独立管理后台脱离微信生态 |
| 数据安全 | 学习数据仅用户自己可见；管理后台需要单独的管理员账号权限，与普通用户体系隔离 |
| 合规 | 明确产品定位为"中医知识学习训练工具"，不提供面向真实患者的诊断/开方建议，避免医疗合规风险 |

## 九、MVP 范围与迭代路线图

**Phase 0（内容准备，先于产品开发）**
- 完成内容管理后台（录入 + AI生成 + 审核）
- 完成 100 首方剂基础数据录入（方名/组成/剂量/六经归类/标准症状/鉴别方剂）
- 每方至少产出并审核通过 3～5 条症状变式，形成可用题库

**Phase 1（小程序 MVP）**
- 学习模式（翻卡）
- 随机抽题
- 基础错题本（仅基于学习模式的主观标记）

**Phase 2**
- 测试模式（选择六经+方剂判分）+ 完整错题本闭环
- 我的-学习进度总览（六经掌握度可视化）

**Phase 3（可选增强）**
- 内容持续扩充（超过100方，兼证/合病题型）
- 学习激励机制（打卡、连续学习天数）
- 视具体情况评估是否加入分享/邀请等传播机制

## 十、开放问题（需你进一步决策）

1. 是否需要**多人/团队协作审核**（比如你带教的学生帮忙审核变式），还是仅你一人审核？这会影响后台的权限设计。
2. 测试模式的判分方式：六经判断错但方剂选对（或反之）算部分得分，还是必须两者都对才算对？
3. 是否需要引用具体的伤寒论/金匮要略条文原文作为答案页补充内容？（涉及是否需要处理原文版权与准确校对的问题）
4. 是否考虑未来商业化（付费解锁题库/会员），如需要，需提前设计内容分级（免费题库 vs 付费题库）。
